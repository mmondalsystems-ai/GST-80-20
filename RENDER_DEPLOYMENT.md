# Deploying GST 80:20 on Render

The repository contains a `render.yaml` Blueprint for the recommended topology:

- one Docker-based Python web service with `pg_dump` included;
- one Render Postgres database;
- one persistent disk mounted at `/var/data/gst8020`;
- database-aware health checks at `/readyz`; and
- HTTPS-only session cookies.

## New Render deployment

1. In Render, create a **Blueprint** and connect this GitHub repository.
2. Render reads `render.yaml`. Confirm the Singapore region and resource plans.
3. Enter a strong `BOOTSTRAP_ADMIN_PASSWORD` when Render prompts for the
   `sync: false` variable. Do not use the local demonstration password.
4. Deploy and wait for `/readyz` to pass.
5. Sign in as `admin@oswalgroup.net` and change the first administrator password.
6. Open **AI Workspace** as Administrator. Paste the Anthropic API key, then
   enable only the approved capabilities and configure current token prices and
   the monthly cost guardrail.

The API key is encrypted in Postgres. `SECRET_KEY`, generated by the Blueprint,
must remain stable because it is also the encryption key for sessions and stored
integration secrets.

## Existing Git-connected Render service

A normal Git-connected web service does not automatically adopt a Blueprint just
because `render.yaml` exists. Either create/sync a Blueprint or apply these values
in the existing service:

| Render setting | Value |
|---|---|
| Runtime | Docker, using the repository `Dockerfile` |
| Dockerfile | `./Dockerfile` |
| Docker context | `.` |
| Health check | `/readyz` |
| `DATABASE_URL` | Internal connection string of the Render Postgres database |
| `SECRET_KEY` | A stable generated secret |
| `SESSION_HTTPS_ONLY` | `1` |
| `VAR_DIR` | `/var/data/gst8020/var` |
| `UPLOAD_DIR` | `/var/data/gst8020/var/uploads` |
| `MAX_UPLOAD_MB` | `64` (per workbook; raise only after memory testing) |
| `BACKUP_DIR` | `/var/data/gst8020/backups` |

Attach a persistent disk at `/var/data/gst8020`. Render disks require a paid
service and limit the service to one instance. Concurrent browser users are still
supported through Postgres, but horizontal scaling is intentionally disabled
because archive files live on the mounted disk.

The disk also means deployments involve a short service interruption: Render
must stop the current instance before mounting the disk on its replacement.
Render does not permit a custom shutdown delay for disk-backed services.

The Docker image intentionally installs PostgreSQL client 18 and the Blueprint
pins Render Postgres to major version 18. The application needs a matching
`pg_dump` to produce the database backup after each successful calculation.
Do not replace the Docker runtime with a bare Python runtime unless `pg_dump` is
installed and verified separately.

## Important migration warning

Changing an existing deployment from SQLite to `DATABASE_URL` on Postgres does
not migrate historical data automatically. Preserve the existing database and
complete an explicit, verified migration before changing the variable. Never
delete the existing disk or SQLite file as a way to resolve a configuration
error.

Render's ordinary service filesystem is ephemeral. Only Postgres and files below
the mounted disk path survive replacements and redeployments. Keep the
installation identity, uploads and generated backups under the configured
`VAR_DIR`/`BACKUP_DIR` paths.
